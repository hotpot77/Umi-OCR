# 公路工程质量管理信息系统（文控 / GLAF）逆向说明与开发路径

> 分析对象：`http://fjhmtd.com:15123/glaf/login.html`  
> 产品厂商：福建华闽通达信息技术有限公司（chinaiss / GLAF / R 平台）  
> 演示账号：`施工六标全角色` / `888888`  
> 分析日期：2026-07-10  
> 分析方式：登录探查 + 静态资源拆解 + 认证抓包 + 页面/菜单遍历 + 公开产品资料交叉验证

---

## 1. 一句话结论

这是一套以 **WBS（工程划分）为中台、以电子文件/质检表格为业务载体、以无编码表单引擎驱动页面** 的公路工程「文控 + 质检」系统。  
**可借鉴的是业务模型与产品路径，不宜直接复刻其低代码运行时。**  
自研同类产品的合理路径是：**先做「WBS + 工序签认 + 质检表单 + 审批归档」MVP，再扩展文控/统计/总控**；整体难度 **高**，但可分阶段落地。

## 2. 产品定位与厂商背景

| 项 | 观测结论 |
|----|----------|
| 登录页标题 | 文控登陆 |
| 系统标题 | 公路工程管理信息系统 / 工程质量管理信息系统 |
| 首页壳标题 | 南天（推送） |
| 厂商 | 华闽通达（2007 起），核心为 **无编码 R 平台 / GLAF** |
| 产品族 | 公路建设项目总控、电子文件信息中心、质检施工版、安全/监督等 |
| 设计哲学 | 「业务与代码分离」；以电子文件标准化反推业务标准化；**WBS 承载全部业务关系** |

公开访谈要点（与本系统高度吻合）：

1. 从质量档案切入，再扩展到安全、计量、进度，最终形成总控。
2. WBS 不是简单树，而是编码规则 + 部位标准 + 文件体系的统一骨架。
3. 质检复杂度远高于计量支付；大项目可达「数十万分项 / 数百万表格」。
4. SpreadJS 用于类 Excel 质检表/报表无编码设计（葡萄城案例可印证）。

## 3. 技术架构（实测）

### 3.1 总体分层

```text
浏览器
  ├─ 登录页 login.html（低代码页面引擎渲染）
  ├─ 主壳 frameset：top / left / content / footer
  └─ 业务页 /glaf/mx/form/page/viewPage?id={pageId}
        ├─ Kendo 树/表格/按钮
        ├─ SpreadJS 类 Excel 质检表
        └─ 规则引擎 pageed / mt* 事件（登录、提交流程、打开子页等）

Nginx
  └─ Resin/4.0.65（Java）
        ├─ com.glaf.* 运行时
        ├─ 表单/数据集/树表/附件/工作流
        ├─ Activiti 任务接口痕迹：/mx/activiti/task
        └─ 服务编排：/mx/serviceorchest/...
```

### 3.2 技术栈清单

| 层 | 技术 | 证据 |
|----|------|------|
| Web 服务器 | Nginx + **Resin 4.0.65** | 响应头 / 415 错误页 `Resin/4.0.65` |
| 后端 | Java，`com.glaf.*` | `ServiceProcessController` 堆栈 |
| 会话 | `JSESSIONID` + `GLAF_COOKIE` + **`GLAF_JWT_COOKIE`** | Cookie 实测 |
| 前端壳 | 传统 frameset + jQuery | `/mx/my/home/main` |
| UI | Kendo UI、Bootstrap、自研 `glaf-web-1.0.0` | 静态资源 |
| 表格引擎 | **SpreadJS ~4.17**（xlinsload） | 脚本路径 / 葡萄城案例 |
| 轻量 MVVM | Vue.min.js（局部） | 登录页引入 |
| 工作流 | Activiti 风格任务 URL | `/mx/activiti/task?processInstanceId=` |
| 地图/埋点 | 百度地图 SECKEY 等 | localStorage |

### 3.3 认证流程（已打通）

```text
1) GET  /glaf/mx/login/getLoginSecurityKey
      → { x_y, x_z }  随机盐/混淆串

2) 前端拼密码：x_y + 明文密码 + x_z
      （登录页规则把用户名/密码参数映射为 x / y）

3) POST /glaf/mx/login/doLogin?x=<urlencoded用户名>&responseDataType=json
      body: x=...&y=<混淆后密码>

4) 成功后下发：
      - GLAF_JWT_COOKIE（HS256 JWT，含 userId/actorId/token/exp）
      - GLAF_COOKIE（长会话票据）
      - JSESSIONID

5) 跳转 /glaf/mx/my/home → frameset 主壳
6) 轮询 /glaf/mx/user_status → {"user_status":"SUCCESS","user_id_md5":"..."}
```

JWT payload 示例字段：`userId`、`GLAF_LOGIN_ACTORID`、`systemName=default`、`token`、`LOGIN_IP`、`exp`。

> 安全观察：HTTP 明文、密码仅前端混淆非强加密、JWT 有效期极长。自研时应改为 HTTPS + 标准哈希/挑战应答 + 短时 access/refresh token。

### 3.4 页面与数据引擎（核心难点）

几乎所有业务界面都不是手写 Vue/React 页面，而是：

1. **页面定义** `pageId`（32 位 hex）
2. **规则定义** `pageRuleId` / `pageed`（事件编排：click → mtLogin / mtSubmit / 打开子页）
3. **数据集** `/mx/dataset/allJSON|previewJSON?id=`
4. **表格数据** `/mx/form/data/gridData`
5. **树表数据** `/mx/form/treelist/gridData`
6. **菜单数据** `/mx/form/menuData/data`
7. **附件** `/mx/form/attachment?method=upload|download|remove|getFilesByRandomParent`
8. **流程** `/mx/form/workflow/defined/submit` 及 mtAssign/mtBack/mtReject 等

首页施工页 `viewPage?id=fe95d5e417554a91aa86ed318ecea9e1` 实测：

- 标题：`首页-施工`
- 角色码含：`SGGL`、`R006`、大量 `dy00*`（全角色演示账号）
- 卡片：待办任务 / 已办任务 / 分项完成 / 工序完成
- 任务 Tab：待办 / 已办 / 退回 / 全部
- 已挂接 Activiti 任务查看链接

这解释了为何系统「看起来像很多模块」，但底层是 **同一套表单运行时 + 不同 pageId/数据集配置**。

### 4.1 关键业务闭环

```text
工程划分(WBS)
   ↓ 挂接部位/工序
工序签认 / 质检表格（施表-xx）
   ↓ 填报、校核、签章
任务流转（施工→监理→业主等角色）
   ↓
文件管控 / 打印 / 归档元数据
   ↓
统计分析（分项/工序完成率）
```

### 4.2 质检表形态（实测）

| 表单 | 形态 | 说明 |
|------|------|------|
| 混凝土构件养护记录（施表-43） | 结构化表单 | 单位/分部工程、养护方式勾选、签字栏 |
| 路基路面平整度检测原始记录（施表100） | SpreadJS 网格 | 多测点录入、类 Excel 表头合并 |

工具栏常见能力：保存、一键打开、导入附件、挂接评定册、校核报告、打印、历史记录。

### 4.3 WBS 特征

- 专业：路基 / 桥梁 / 隧道 / 房建 / 交安 / 绿化 / 机电等
- 桩号段编码：如 `K89+710~K102+915.41`
- 过滤前缀：K / ZK / YK / AK…（左右幅、匝道等）
- 左树右表是全系统统一交互范式

## 6. 领域模型（建议自研时采用）

```text
Project（项目/合同段）
  └─ WbsNode（单位/分部/分项/工序，树 + 编码 + 专业类型）
        ├─ Drawing（图纸）
        ├─ ProcessTask（工序签认任务）
        │     ├─ FormInstance（质检表实例，绑定模板）
        │     ├─ ChecklistItem / MeasuredValue（检查项与实测值）
        │     ├─ Attachment / Signature（附件与签章）
        │     └─ WorkflowInstance（审批轨迹）
        ├─ DocumentFile（文控文件，元数据 + 原文）
        └─ EvaluationBook（评定册/交工评定汇总）

Org / Role / User（业主、施工、监理、试验等多角色）
FormTemplate（施表模板库，按地方标准可配置）
RuleEngine（可选：合格率计算、自动评定、超时）
```

标准依据建议对齐：

- `JTG F80/1-2017` 公路工程质量检验评定标准
- `JTG G10-2016` 施工监理规范
- 地方用表 / 电子文件归档规范（文控合规关键）

## 7. 逆向路径与难度评估

### 7.1 可逆向程度

| 维度 | 难度 | 说明 |
|------|------|------|
| UI/菜单/业务流程 | ★★☆☆☆ 低 | 可登录遍历，截图与流程清晰 |
| 前端静态资源 | ★★★☆☆ 中 | JS 已压缩，但登录/API 路径可提取 |
| 认证协议 | ★★★☆☆ 中 | 已完整打通 doLogin |
| 表单页配置模型 | ★★★★☆ 高 | pageId/规则/数据集耦合深 |
| 质检计算与评定规则 | ★★★★☆ 高 | 藏在模板与后端规则，需逐表验证 |
| 无编码平台本身 | ★★★★★ 极高 | 等同重做 R 平台，不建议作为目标 |
| 电子签章/归档合规 | ★★★★☆ 高 | 涉及 CA、元数据四性检测 |

### 7.2 推荐逆向策略（合法、高效）

1. **黑盒业务逆向**（本报告主体）：菜单 → 页面 → 表单 → 状态机。
2. **接口契约逆向**：对关键页抓 XHR，整理 OpenAPI 草案。
3. **模板库逆向**：导出/截取施表模板字段、计算项、签字栏。
4. **标准对齐**：用国标/地标校验系统行为，而不是抄实现。
5. **竞品对照**：华岩、恒智天成、筑业、鲁班质检等，抽取共性能力清单。

> 注意：本仓库分析仅用于学习与自研同类产品设计，勿直接复制厂商专有资源/模板商用。

### 7.3 与另一套「鲁班/iworks」系统对比

同账号体系下曾分析过 `iworks-web-new`（React 微服务网关）。对比：

| | GLAF 文控质检 | iworks/鲁班数字平台 |
|--|---------------|---------------------|
| 架构 | 单体/模块化 Java + 低代码页 | 网关 + 多微服务 + 多前端 |
| 核心 | 文件/质检表驱动 | 待办聚合 + BIM/投资/质检 |
| 前端 | frameset + Kendo + SpreadJS | React SPA |
| 痛点 | 配置复杂、老 UI | 首页统计极慢、请求风暴 |
| 自研借鉴 | **领域模型更值得学** | 微服务拆分与性能反例 |

**做同类质检文控产品，优先学 GLAF 的业务骨架；做总控大平台，再参考 iworks 的模块边界。**

## 8. 开发类似产品：总体路径

### 8.1 产品策略（不要一上来做无编码平台）

```text
阶段 A  MVP：合同段质检闭环
阶段 B  文控增强：模板库 + 签章 + 归档元数据
阶段 C  总控扩展：计量前置、安全、进度共用 WBS
阶段 D  （可选）低代码/模板设计器，降低实施成本
```

华闽通达自身也是「先档案/质检 → 再总控 → 再无编码平台」走了十余年。自研应压缩路径，但 **不要跳过 WBS 与表单标准化**。

### 8.2 建议技术选型（现代替代）

| 能力 | GLAF 现状 | 建议自研选型 |
|------|-----------|--------------|
| 后端 | Java/Resin 老栈 | Java Spring Boot 3 / Go，模块化单体起步 |
| 前端 | frameset + Kendo | Vue3/React + 设计系统 |
| 表格 | SpreadJS（商业） | SpreadJS 或 FortuneSheet / Handsontable（按预算） |
| 流程 | Activiti | Camunda 7/8 或 Flowable |
| 权限 | 角色码字符串 | RBAC + 数据范围（标段/工区） |
| 文件 | DB/FTP/目录多模式 | MinIO/S3 + 元数据库 |
| 移动 | 未见本演示重点 | Flutter/uni-app 现场填报 |
| 部署 | HTTP 单机感 | HTTPS、容器、可观测性 |

### 8.3 模块优先级

**P0（必须有，否则不像产品）**

1. 组织/项目/标段与角色权限  
2. WBS 工程划分（导入、树编辑、编码规则）  
3. 质检模板库（先覆盖路基/桥梁/隧道高频施表 20–50 张）  
4. 工序签认任务流（施工自检 → 监理抽检/签认）  
5. 附件、打印、基础待办台  

**P1（形成文控竞争力）**

6. 文件管控（按 WBS 归集、版本、收发）  
7. 电子签章与操作留痕  
8. 自动计算合格率/评定汇总  
9. 统计分析看板  
10. Excel 导入导出与批量生成用表  

**P2（总控与规模化）**

11. 计量支付前置（质量资料齐套才可计量）  
12. 试验室数据引用（一数一源）  
13. 档案四性检测与移交包  
14. 模板设计器（无编码的最小子集）  
15. BIM/GIS 挂接（赋能，而非先做）

## 9. 详细开发计划

### 阶段 0：需求与标准基线

- 选定目标省份用表（或交通部通用表）  
- 梳理角色：施工员/质检员/监理/业主/资料员  
- 输出《施表字段字典》《WBS 编码规范》《状态机》  
- **交付物**：PRD、领域模型 ER 图、表单清单 Top50  

### 阶段 1：基础平台

- 账号、RBAC、多标段数据隔离  
- 项目初始化向导  
- 文件存储与审计日志  
- **交付物**：可登录的空壳 + 权限演示  

### 阶段 2：WBS 中台

- 树 CRUD、拖拽、导入导出  
- 部位类型 → 默认工序/用表映射  
- 与任务模块的关联键设计  
- **交付物**：工程划分模块可用  

### 阶段 3：质检 MVP

- 表单模板（JSON Schema 或 Excel 模板双轨）  
- 实例填报、校验、保存  
- 简易审批流（3–5 节点）  
- 待办首页  
- **交付物**：从划分到签认的闭环 Demo  

### 阶段 4：文控与归档

- 文件与表单实例双向挂接  
- 元数据（形成者、时间、版本、责任者）  
- 打印/PDF、目录树、检索  
- **交付物**：可演示「业务产生即归档」  

### 阶段 5：评定与统计

- 分项/分部/单位工程汇总评定  
- 工序完成率、资料完成率、超时预警  
- **交付物**：管理层看板  

### 阶段 6：实施工具化

- 模板设计器、规则配置、项目克隆  
- 性能：树懒加载、统计预聚合、附件 CDN  
- 安全：HTTPS、国密/CA 对接（按客户要求）  

> 难度刻画：阶段 1–3 主要是常规业务系统工程；阶段 4–5 开始出现行业规则与合规复杂度；阶段 6 接近平台化，投入显著上升。

## 10. 关键技术风险与应对

| 风险 | 表现 | 应对 |
|------|------|------|
| 表格数量爆炸 | 单标段数十万张 | 按工序懒生成；模板实例化；归档冷热分层 |
| 规则地方化 | 各省用表不同 | 模板/规则可配置，核心引擎稳定 |
| Excel 体验依赖 | 用户只认表格 | 保留网格编辑，但数据入库结构化 |
| 审批与签章 | 法律效力与四性 | 早接 CA；元数据与原文分离存储 |
| 性能 | 深树 + 大统计 | 物化路径、预聚合、列表投影 |
| 范围失控 | 想一次性做总控 | 严格按 P0→P2 砍需求 |

## 13. 最终建议

1. **学业务，不抄平台**：把 GLAF 的 WBS + 文件 + 工序签认模型吃透。  
2. **先闭环，后平台**：MVP 只做质检签认与基础文控。  
3. **用现代栈重做运行时**：避免 frameset/低代码历史包袱。  
4. **把标准与模板当产品资产**：真正护城河是用表库、规则库与实施方法论。  
5. **难度预期**：做出可售卖的合同段质检文控系统，属于「高复杂度行业应用」；做出对等 R 平台，属于「平台级工程」，应单独立项。  
6. **复用开源与对标清单**：见同目录 [`REFERENCE_INVENTORY.md`](./REFERENCE_INVENTORY.md)（若依/Warm-Flow/Univer/文控/签章及国内外商业对标）。
