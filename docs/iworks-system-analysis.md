# 工程数字管理平台（iworks-web-new）后端数据与系统重难点分析

> 分析对象：`http://221.203.107.254:8182/iworks-web-new/#/home`  
> 项目：辽宁省本溪至集安高速公路本溪至桓仁（辽吉界）段 PPP 项目（本桓高速）  
> 分析方式：浏览器登录探查 + DevTools Network 抓包 + 静态资源探测  
> 分析日期：2026-07-10

---

## 1. 系统概览

该系统是面向高速公路工程的 **工程数字管理平台**（鲁班/中铁体系），前端为 React SPA（Create React App 产物），后端经 Nginx 统一网关：

```text
http://221.203.107.254:8182/gateway/{service}/...
```

### 1.1 主要业务模块

| 模块 | 说明 | 观测到的服务前缀 |
|------|------|------------------|
| BIM管理系统 | 模型列表、缩略图、版本管理 | `/gateway/luban-bim-web/`、`/gateway/builder/` |
| 质检评定系统 | 工序检验/交工评定（施工+监理） | `/gateway/luban-process-inspection-web/` 等 |
| 投资管理系统 | 合同清单、计量支付 | `/gateway/` 下清单/合同相关服务 |
| 进度/工序检验 | 进度统计看板 | `/gateway/iworks/` 等 |
| 物料/物资、质量、安全、文档、档案 | 菜单可见 | 多微服务 |
| 组织架、计支宝、试验室 | 其它系统入口 | 独立子系统 |

首页是跨模块 **待办工作台**，聚合投资管理、质检评定等业务待办。

### 1.2 技术架构特征

- **网关聚合微服务**：`auth-server`、`pdccommon`/`pdcommon`、`iworks`、`builder`、`luban-bim-web`、质检相关服务等
- **认证**：`POST /gateway/auth-server/auth/token`；请求头使用 `Access-Token` / `jwt-access-token`（非标准 `Authorization: Bearer`）
- **前端配置**：`config.js` 写死 `BASEURL = http://221.203.107.254:8182/gateway`
- **协议**：HTTP（非 HTTPS）；`Cache-Control: no-store`；未见 Gzip/Brotli；HTTP/1.1
- **登录密码传输**：MD5 摘要（弱安全实践）

## 2. 后端数据与接口观测（关键证据）

### 2.1 首页工作台 —— 最严重性能问题

| 接口（示意） | 耗时 | 问题 |
|--------------|------|------|
| `allBusinessTypeCount` | **~39.9s** | 全业务类型计数极慢 |
| `taskDeptStatusCount` | **~25.2s / ~40.1s** | 部门/状态聚合计数极慢 |
| `todo` | pending / 长时间挂起 | 待办列表被阻塞 |
| `list` | ~1.9s / **615KB** | 列表体量大 |

页面表现：待办表长时间 loading；总传输约 **8.3MB / 77 请求**，时间线可拉到数分钟。

**结论**：首页不是“前端慢”，而是 **统计聚合 SQL/服务调用成为主瓶颈**。

### 2.2 质检评定系统 —— 树结构 + 大积压

关键接口：

- `tree?section_id=...`：**~1.99s / 14.8KB**
- `folders`：**~2.10s / 63.5KB**
- `tree?dept_id=...`：**~1.64s / 59.7KB**
- `page?pageIndex=1&pageSize=50`
- `statistics?type=2&wbsId=...`

业务数据特征：

- 统计条：**总计 1959 | 已通过 0 | 待操作 1959 | 已超时 1959**
- 表格分页显示约 51 条 / 2 页（与 1959 总量口径不一致）
- 多 Tab：开工报告、工序检验(施工/监理)、交工评定(施工/监理)
- 批量：导出、复审、导入 Excel

**结论**：WBS/文件夹树一次性下发 + 超大待办积压 + 多状态统计，是质检模块的核心难点。

### 2.3 投资管理系统 —— 深层级清单

- 合同清单树：`A100` → `101` → `101-1` → …
- 分页：**100 条/页 × 约 43 页**
- 部分 `list`：**~1.73s**
- 页面资源合计约 **7MB**，Finish ~**6.1s**
- 细粒度接口多：`getUnitConfig`、`getRuleIdByProjectId`、`getByRuleId`、`set_curr_project` 等

**结论**：清单层级深、金额汇总与导入编辑并存，后端需支撑树查询 + 大批量分页 + 规则配置。

### 2.4 BIM 管理系统 —— 首屏资源重

- 模型列表约 34 条，分页展示
- 模块加载约 **12.7MB / 58 请求 / Finish ~12.5s**
- `authgroup/192`：**~65.4KB / ~0.8–0.9s**（权限组过大）
- `getApplicationPackageInfo` / `getAppAllocationPackageInfo`：**~26–61KB**
- `page` 小数据也有 **~868ms** 延迟

**结论**：BIM 首屏被静态资源 + 权限/包信息接口拖累，列表本身数据量不大。

### 2.5 跨模块重复调用

几乎每个子系统进入时都会重复请求：

1. `/auth-server/authgroup/192`（可达 **65KB+**）
2. `get-user-detail`
3. 企业/项目配置类接口

会话内重复拉取，浪费带宽并拉长切换模块耗时。

### 2.6 静态资源与网关侧问题

| 项 | 观测 |
|----|------|
| 主 CSS chunk | `5.99d577d8.chunk.css` ≈ **533KB**，无压缩 |
| 主 JS vendor | `5.6ead3a24.chunk.js` ≈ **182KB**，无压缩 |
| HTML Cache | `no-store, no-cache` |
| HTTP | 仅 HTTP/1.1，未见 HTTP/2 |
| CORS | `Access-Control-Allow-Origin: *` |
| 安全 | 明文 HTTP + MD5 密码摘要 |

## 3. 系统重难点

### 难点一：跨业务待办与实时统计（首页）

- 首页需聚合多业务线（投资、质检等）的待办/已办/退回状态
- `*Count` 类接口 25–40 秒，说明后端很可能是 **实时全表扫描/多服务串行汇总**
- 待办列表与统计互相拖累，用户感知为“系统卡死”

### 难点二：质检评定工作流与 WBS 树

- 施工/监理双轨、多阶段审批
- 深层级工程树（工区 → 分项 → 桩号）
- 1959 条待操作且全部超时，说明流程推进与超时策略本身也是业务难点
- 统计口径与列表分页口径不一致，增加联调与验收成本

### 难点三：投资清单的层级金额一致性

- 合同清单多级汇总（章 → 节 → 细目）
- 导入/编辑/历史记录与金额合计强一致要求
- 深树 + 大分页下，任何局部修改都可能触发重算

### 难点四：微服务网关下的会话与权限一致性

- 多 token 头、企业切换、`productId`、子系统独立前端（`luban-*-web`）
- 权限组一次下发过大，权限模型复杂
- 模块切换重复鉴权/拉配置，状态易不一致

### 难点五：BIM/大资源与工程元数据

- 模型缩略图、版本、专业、标段归属
- 包信息/企业配置体积大
- 后续若上轻量化浏览/GIS，后端与 CDN 压力会进一步放大

### 难点六：安全与部署基线薄弱

- HTTP、弱密码摘要、宽松 CORS、调试开关（`lbsvDebug = true`）
- 对内网可用，但对公网或跨网访问风险高

## 4. 需要优化的地方（按优先级）

### P0 —— 立刻做（体验与可用性）

1. **重写首页统计接口**
   - `allBusinessTypeCount` / `taskDeptStatusCount` 改为预聚合（定时任务 + Redis/汇总表）
   - 目标：**<200ms** 返回计数
   - 待办列表与统计解耦：先出列表，计数异步刷新

2. **给统计/树查询加索引与限流**
   - 索引候选：`projectId`、`sectionId`、`wbsId`、`status`、`deptId`、时间字段
   - 对超慢接口加超时、熔断、降级默认值

3. **开启传输压缩与缓存**
   - Nginx 开启 `gzip`/`brotli`
   - 静态资源改为长期缓存 + hash 文件名（当前 HTML 全站 no-store 过严）
   - 目标：首屏传输下降 **50%+**

### P1 —— 短期（1–2 个迭代）

4. **权限与用户信息会话级缓存**
   - `authgroup`、`get-user-detail`、企业配置只在登录/切换企业时拉取
   - 前端 memory/sessionStorage + `ETag`/`If-None-Match`

5. **树接口懒加载**
   - `tree`/`folders` 按展开节点分页或按层加载
   - 避免一次下发 60KB+ 全树

6. **合并聊天式小接口**
   - 将 `getUnitConfig` + `getRuleId` + `getByRuleId` + 用户信息等合并为模块 `bootstrap` 接口
   - 减少 40–70 次/页的请求风暴（HTTP/1.1 下尤其致命）

7. **质检积压治理**
   - 查清 1959 全超时原因（规则过严 / 未发起即计超时 / 历史脏数据）
   - 列表默认过滤“待我处理”，历史超时归档

8. **统一统计口径**
   - 顶部 `statistics` 与表格 `page.total` 必须同源同过滤条件

### P2 —— 中期架构

9. **HTTP/2 + HTTPS**
10. **字段裁剪 / 投影查询**（列表不返回详情大字段）
11. **BIM 资源 CDN + 缩略图 WebP/懒加载**
12. **微前端独立部署与共享壳**（已有多 `*-web` 迹象，需统一鉴权与公共依赖）
13. **可观测性**：`Server-Timing`、慢查询日志、前端 RUM（首页 P95）
14. **安全加固**：HTTPS、停用 MD5 登录、收紧 CORS、关闭生产 debug

## 5. 优化收益预估（基于本次抓包）

| 优化项 | 预期收益 |
|--------|----------|
| 首页 Count 预聚合 | 首页可用时间从 **数十秒** 降到 **1–2 秒内** |
| authgroup 缓存 + 裁剪 | 每会话少传 **200KB+**，模块切换明显加快 |
| Gzip/Brotli | 静态+JSON 体积约降 **60–70%** |
| 树懒加载 | 质检首屏少等 **1.5–2s** |
| 请求合并 | 减少排队，HTTP/1.1 下收益显著 |
| BIM 资源优化 | 12MB 级首屏有望降到数 MB |

## 6. 建议落地顺序

```text
1) 首页统计预聚合 + 列表解耦
2) Nginx 压缩/缓存 + 慢接口索引
3) 权限/配置会话缓存
4) 质检树懒加载 + 统计口径修复
5) 投资清单查询与导入性能专项
6) HTTPS/鉴权规范化与可观测性
```

## 8. 一句话结论

该平台业务完整、微服务拆分清晰，但 **首页聚合统计（25–40s）是当前最大可用性瓶颈**；其次是 **质检 WBS 树慢查询与超大积压、跨模块重复拉权限、静态资源未压缩、HTTP/1.1 请求风暴**。优先做“统计预聚合 + 压缩缓存 + 会话级权限缓存 + 树懒加载”，即可显著改善体感与后端压力。
